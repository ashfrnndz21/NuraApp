## How to read the table

- **Issue** is the GitHub state. Several stories are delivered but still open, because a PR body said "Closes #a, #b, #c" (a single `Closes` keyword before a comma list) and GitHub closes only the first issue in such a list — see *Issue state* below. A PR that repeats the `closes #N` keyword before every number closes all of them, which is how most of the PRs behind this re-audit are written. Judge a story by its status, not its issue state.
- **Backend** is the route and module that carry the story, the merged PR, and the test that shows the acceptance.
- **Web** is the screen or component under `web/src` that surfaces it; "none" if nothing on the web does; "n/a (system)" for a service with nothing a person sees.
- **Substitute** is the ADR 0001 stand-in where part of the story is native-only.
- **Checkpoint** is the one in `docs/checkpoints.md` that shows it (checkpoints run 2–28; 24–28 are the web-parity walks added by #137–#177 and were largely uncited by the last audit).
- **Status**:
  - **done**: the acceptance is met in code and a web surface exists, or it is a system story with nothing to surface;
  - **backend-only**: the acceptance is met on the API, a person would use it, and no web screen does;
  - **missing**: part of the acceptance is not met in code (the note says which, using "Met: … Not met: …" where part of it holds);
  - **in flight**: covered by open work actively landing. As of this audit nothing is in this state — the four issues (#61, #63, #8, #74) the last audit tied it to are all closed and their PRs merged; each row that was "in flight" is re-classified above as `done` or `missing` on what the code now shows.

## Operator decisions

- **Nudges stay one a day, not two** (E17-03, #71). Decided when #119 merged; the story's "two a day" is superseded. #121 keeps one cap, and #138's web nudge card enforces the same cap client-side (it shows the one nudge the backend handed over, nothing more).
- **E05-01's brief is deliberately never edited.** #147 built the T-3 trigger and the one-page budget, but kept the pre-visit brief itself read-only by design (`app/reasoning/visits/brief.py`'s docstring): what he or his chief want to add or remove goes on the *questions* card (E05-02), which is editable on a yes. This satisfies "editable" as a product decision about which card is the editable one, not as an unmet gap.
- **E13-02's "call clinic" row is built** (#147, `app/safety/not_feeling_well.py` `DECISION_TABLE`, the `CALL_CLINIC` row). The red flag always wins: `Situation.calls_the_clinic` returns `False` whenever `red_flag` is true, checked directly in the code for this audit, so nothing about this row can pre-empt or delay the ambulance path. `docs/trust/clinical-sign-off.md` confirms the same reviewed position. The operator's earlier flag on this item (a clinical decision needing a safety review) is resolved.
- **E19-05's hospital-naming red-flag tiers are built and gated, not yet live.** `app/safety/red_flags.py`'s two-tier table (ambulance vs. same-day, with the named panel hospital) exists, is fully tested (`tests/test_red_flag_escalation.py`, 225 tests) and is walked by checkpoint 20 — but it only renders when `Settings.red_flag_tiers` is true, set by `NURA_RED_FLAG_TIERS=1`. `make dev` sets this for local/test use; **neither `fly.toml` nor `render.yaml` sets it**, so every production deployment defaults to the old, stricter behaviour: every red flag says "Call the ambulance now" regardless of tier. `docs/trust/clinical-sign-off.md` lists this switch, blocking on an out-of-hours wording question and the regulatory adviser's answer to SaMD review question 10. This was checked specifically for this audit as a possible safety gap (a clinical decision-support feature that shipped code before sign-off) and found to be properly gated: it cannot reach a real family until both the flag is set and the sign-off table is filled in. Marked `done` below because the story's own acceptance (escalation within a minute, the panel hospital named) is met in code and tested; the sign-off is tracked separately under E16-03, where it belongs.
